Designing & Changing Data

Reading is half of SQL. The other half creates the structures and keeps data correct as it changes.

DDL — defining structure

  • CREATE TABLE — columns, types, keys, constraints.
  • ALTER TABLE — add, change or drop columns; add constraints.
  • CREATE INDEX — make a lookup fast. Index the columns you filter and join on; every index also costs writes and space.

DML — changing rows

  • INSERT adds rows; list the columns explicitly.
  • UPDATE ... SET ... WHERE ... changes rows — and the WHERE is the whole safety mechanism.
  • DELETE FROM ... WHERE ... removes rows, with the same warning.

Run the SELECT first. Before any UPDATE or DELETE, run the identical WHERE clause as a SELECT and count the rows. Wrap related statements in a transaction so they all apply or none do. An unguarded UPDATE has no undo.

Transactions and integrity

ACID — atomicity, consistency, isolation, durability — is what lets several statements be treated as one unit. Use BEGIN … COMMIT (and ROLLBACK) so a partial failure never leaves half-applied data. Let the database enforce uniqueness and foreign keys rather than trusting each application to check first.

Reading a schema and writing for others

Name things clearly, choose the narrowest correct type, comment the non-obvious, and format your SQL so the next person can read it. A query is a document as much as an instruction.
