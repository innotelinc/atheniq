Name It, Test It, Own It

A prompt that lives in someone's notes disappears when they change team. A prompt library turns individual tricks into a shared asset — but only if each entry is documented well enough to be trusted and tested often enough to be true.

What an entry contains

  • Name and purpose. What job it does, in one line.
  • The prompt text, with placeholders clearly marked.
  • An example input and an example good output.
  • The review gate. Who checks the result, and what they check.
  • An owner. The person who keeps it current.
  • A test case. One input whose correct output you can recognise, so a change can be detected.

Why test cases matter

Tools change models, and models change behaviour. A prompt that produced exactly what you wanted in March can quietly produce something different in June. Without a test case, nobody notices until the output is in front of a customer. With one, a weekly run takes two minutes and tells you whether the entry still works.

Library hygiene

  1. One job per entry — a prompt that does three things breaks in three ways.
  2. Keep prompts free of real customer data; use placeholders.
  3. Version the entry; do not edit over a version a team depends on.
  4. Retire entries loudly. A stale prompt is worse than no prompt because people trust it.

Prompts from the internet

Public prompt collections are useful inspiration and unreliable infrastructure. You do not know what data they send, what instructions they hide, or whether the author tested them. Treat a copied prompt like copied code: read it, remove anything that sends data somewhere unexpected, and test it before it touches a real workflow.

Try this

Take your most-used prompt and write the full library entry for it, including a test case and a named owner. Then ask a colleague to run it from the entry alone. If they get a usable result without asking you a question, the entry is good enough to share.
